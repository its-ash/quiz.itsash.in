Strings & Text

Immutability traps, f-string evaluation order, encoding surprises, and the methods that quietly return new objects instead of mutating in place.

Q1. What does the following code print?

snippet.py 
s = "Hello, World"
s.replace("World", "Python")
print(s)
Show Answer

Answer: A Hello, World

Strings are immutable in Python. .replace() (like .upper(), .strip(), .lower(), and every other "modifying" string method) does not change s in place — it computes and returns a brand-new string object. Because the return value here is never assigned back to s, the original variable still points at the untouched "Hello, World". Option B is the tempting mistake of assuming methods mutate the receiver, as they do for lists. There's no item assignment happening (C), and .replace() returns a string, never None (D) — only a handful of in-place methods like list.sort() return None.

Q2. A teammate reports that empty/whitespace-only usernames are slipping past validation.

What does this function actually return for validate_username(" ")?

validate.py 
def validate_username(name):
    name.strip()
    if len(name) == 0:
        return "empty"
    return name

print(validate_username("   "))
Show Answer

Answer: B "   " (the three spaces, unchanged)

name.strip() returns a new stripped string, but that result is discarded — the local variable name still refers to the original three-space string. len(name) is therefore 3, not 0, so the "empty" branch never runs and the untrimmed spaces are returned as if they were a valid username. This is the single most common beginner bug with immutable strings; the fix is name = name.strip(). Nothing here raises an error (D), and it never reaches "" (C) because that would require reassignment first.

Q3. What gets printed, and in what order?

fstring_order.py 
def log(msg):
    print(f"LOG: {msg}")
    return msg.upper()

name = "world"
greeting = f"Hello, {log(name)}!"
print(greeting)
Show Answer

Answer: C LOG: world then Hello, WORLD!

f-strings evaluate embedded expressions eagerly, left to right, at the point the f-string literal is executed — before the final string is assembled. So log(name) runs first (printing "LOG: world" since msg is still the original lowercase arg at print time inside log), returns "WORLD", and only then does the f-string interpolate that return value into "Hello, WORLD!", which prints second. Functions are fully valid inside f-string braces (ruling out D); the return value ("WORLD"), not the pre-call value, is what gets interpolated (ruling out A/B ordering confusion).

Q4. What does this print, and why does the second line differ from what most people expect?

identity.py 
a = "café"
b = "café"
print(a is b)

x = "café".encode("utf-8")
y = "café".encode("latin-1")
print(x == y)
Show Answer

Answer: B True (or possibly False) then False

Idiom: a is b checks object identity, not equality — it happens to often print True here because CPython aggressively interns short string literals that look like identifiers at compile time, but this is a CPython implementation detail, never a language guarantee (a longer or dynamically-built string would reliably be False). Never rely on is for string comparison — use ==. Second: encoding is not canonical. "café".encode("utf-8") represents é as the two bytes b'\xc3\xa9', while "café".encode("latin-1") represents it as the single byte b'\xe9' — same text, different byte sequences, so x == y is False. Option D is wrong because Latin-1 covers the full 0–255 range and happily encodes é (U+00E9) without error; the danger with Latin-1 is silent misdecoding of higher Unicode code points, not an exception here.
